# Архитектурные решения Microscope

Документ фиксирует технические архитектурные решения проекта.

Связанные документы:

- [domain.md](./domain.md) — бизнес-правила карточек;
- [storage.md](./storage.md) — localStorage, JSON и валидация;
- [stack.md](./stack.md) — версии технологий;
- [style.md](./style.md) — соглашения о CSS.

## 1. Тип приложения

Проект — клиентское SPA без серверной части.

- Точка входа: `src/main.tsx`.
- Корневой компонент: `App` из `src/app.tsx`.
- Preact монтируется напрямую в `document.body`; `body` — корневой контейнер приложения и стилизуется напрямую, без класса-обёртки. `App` рендерит фрагмент, отдельного `#app` нет.
- Данные хранятся в браузере: в памяти, `localStorage` и JSON-файлах.
- Серверный API, база данных и авторизация отсутствуют.

## 2. Разделение ответственности

Код разделён по слоям:

- `src/app.tsx` — оркестратор: состояние открытых модалок и обработчики действий.
- `src/components/` — UI-компоненты.
- `src/config/` — UI-конфигурация и тексты карточек.
- `src/stores/` — состояние и операции над доменной моделью.
- `src/types/` — доменные типы.
- `src/utils/` — хранение, импорт/экспорт и браузерные API.
- `src/style.css` — единая точка стилизации.

`App` не содержит разметки карточек и форм: он связывает stores, компоненты и модальные окна.

## 3. Визуализация графа

Для графа используется React Flow (`@xyflow/react`).

Ключевое решение: **один React Flow-узел соответствует одному периоду**.

Внутри узла периода обычным DOM-деревом отображаются:

- карточка периода;
- вертикальный список событий;
- колонки сцен справа от событий.

Почему так:

- события и сцены не требуют собственных рёбер;
- проще сохранить визуальную вложенность;
- меньше узлов и связей в React Flow;
- проще управлять вложенными карточками.

Следствия:

- события и сцены не являются отдельными nodes;
- связи существуют только между периодами;
- высота узла периода определяется содержимым;
- ширина периода фиксирована CSS-токенами и синхронизирована с JS-позиционированием.

Иерархия карточек описана в [domain.md](./domain.md).

## 4. Позиционирование периодов

- Периоды располагаются горизонтально.
- Позиция по X вычисляется как `index * PERIOD_STEP`.
- `PERIOD_STEP` в `CardFlow.tsx` синхронизирован с шириной карточки периода и отступом из CSS.
- Ширина карточки периода рассчитывается через `calc()` из ширины события, отступа и ширины сцены.
- При изменении CSS-геометрии периода нужно проверить и, при необходимости, обновить `PERIOD_STEP`.

Правила добавления периодов описаны в [domain.md](./domain.md).

## 5. Управление состоянием

Состояние реализовано через `nanostores`.

Основные atoms:

- `cardsStore` — массив периодов;
- `settingNameStore` — название сеттинга.

Решения:

- stores разделены по доменам: периоды, события, сцены;
- `cards.ts` используется как barrel-файл публичного API;
- UI подписывается на состояние через `useStore` из `@nanostores/preact`;
- изменения состояния выполняются функциями из `src/stores/`, а не напрямую в компонентах;
- операции создают новые массивы и объекты, не мутируя текущее состояние.

Доменные правила операций описаны в [domain.md](./domain.md).

## 6. Компонентная архитектура

Компоненты разделены на группы:

- карточки (`components/cards/`);
- формы и подтверждения (`components/forms/`);
- шапка и граф (`components/`).

Решения:

- общие кнопки действий вынесены в `CardActionButtons.tsx`;
- `PeriodNode` собирает период, события и сцены;
- `CardForm` — единая форма создания и редактирования карточки;
- `ConfirmModal` — единое окно подтверждения для удаления и сброса;
- `CardFields` — переиспользуемые поля названия и типа;
- `AppHeader` инкапсулирует inline-редактирование названия сеттинга;
- тексты, примеры и конфигурация типов вынесены в `config/cardUi.ts`.

## 7. Стилизация

Принятые соглашения:

- обычный CSS без UI-фреймворков;
- единый `src/style.css`;
- дизайн-токены в `:root`;
- BEM-подобные классы;
- CSS-тултипы через `data-tooltip`;
- без inline-стилей в TSX для оформления.

Подробные правила вынесены в [style.md](./style.md).

## 8. Работа с браузерными API

Решения по совместимости:

- `crypto.randomUUID()` используется с fallback;
- `localStorage` оборачивается в `try/catch`;
- File System Access API используется при наличии;
- для импорта применяется стандартный `<input type="file">`;
- для сохранения файла предусмотрен fallback через скачивание;
- высота приложения использует `100dvh` с fallback на `100vh`.

Формат хранения и импорта/экспорта описан в [storage.md](./storage.md).

## 9. Доступность

- icon-only кнопки имеют `aria-label`;
- тултипы показываются при `:hover` и `:focus-visible`;
- модальные окна имеют `role="dialog"` и `aria-modal`;
- скрытые radio-инпуты сохраняют доступность через label;
- интерактивные элементы должны иметь понятное focus-состояние.

## 10. Инструменты качества

- TypeScript работает в strict mode.
- `tsc --noEmit` выполняется перед production-сборкой.
- ESLint и Prettier обязательны для кода.
- Импорты сортируются автоматически.
- Проверки описаны в [testing.md](./testing.md).

## 11. Осознанно не используются

- серверная часть и база данных;
- Redux/MobX и другие тяжёлые state-менеджеры;
- CSS-фреймворки;
- отдельные React Flow-узлы для событий и сцен;
- маршрутизация: `preact-router` объявлен в зависимостях, но сейчас не используется.
